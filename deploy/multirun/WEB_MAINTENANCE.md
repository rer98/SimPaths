# Maintenance responses and online backups

Install the frontend's `static/service_unavailable.html` at its normal installed
path and include `nginx_maintenance.conf` inside each application server. Keep
the certificate-validation HTTP server unchanged. The installed preview uses
`/etc/nginx/snippets/simpaths-maintenance.conf` for this include.

Nginx can serve this page even while the Python application is stopped. Its
gateway errors become HTTP 503 with `Retry-After: 30` and `Cache-Control: no-store`.
The page does not submit requests automatically. Its Try again link starts a
normal GET at the same service's home page. It advises MultiRun users to check
My Jobs before resubmitting an experiment.

`proxy_intercept_errors off` preserves intentional error responses from the
application, including sign-in and busy/signup forms. Only errors generated by
the proxy itself use the fallback. Private-path denials remain unchanged, and
the internal maintenance URI is not a new public file endpoint. Verify this
distinction with an isolated native Nginx before reloading the public site.

The native proof uses ephemeral loopback ports and a fictional upstream, then
terminates only its own Nginx process. It checks healthy traffic, intentional
application errors, single handling of a POST, the outage response, internal-path
denials and subsequent recovery. It does not stop either public application:

```bash
python3 deploy/multirun/nginx_maintenance_proof.py \
  --page /opt/simpaths-online/JAS-mine-web/static/service_unavailable.html \
  --output /var/tmp/simpaths-maintenance-proof
```

Run with permission to launch the installed Nginx binary; use a fresh output
directory. The proof's temporary worker uses the normal `www-data` identity when
run by root. A guarded installation must validate `nginx -t` before a graceful
reload and preserve the previous site file for rollback.

This makes an interruption understandable; it does not provide a second running
frontend. The current schema-035 installer uses an idle MultiRun window, with no
active or queued model/preparation work, before reloading its private/public
processes. A failed update can extend that window. Do not equate preserved
process identities with uninterrupted interactive controls.

Online backup captures SingleRun registry state and closed exports first under
the SingleRun protection fence, then releases that fence before checking,
compressing and encrypting bulk MultiRun files. A protected SingleRun operation
can still be temporarily unavailable during its own capture. Existing model
engines continue to run; mutable current output is omitted. The SQL snapshot and
captured SingleRun files continue to represent the same recovery point.

Before choosing that recovery point, backup acquisition can wait up to 60 seconds
for an ordinary SingleRun control, cleanup or notification operation to finish.
It does not force that operation to stop. The ordinary control/removal paths
remain nonblocking. A prolonged lock or database error still stops the new
capture safely. The focused `backup_coordination_proof.py` checks contention,
timeout, ordinary controls and early release against disposable PostgreSQL,
alongside real GNU find inventories and both closed-export capture modes.

Visualiser housekeeping and summary locks have bounded waits during capture.
An active processor's incomplete publication remains omitted. A sustained lock,
changed file or invalid receipt still aborts the new backup; previous recovery
copies remain intact. The availability proof covers file fences, native SQL
restore, encryption and both streamed and ordinary SingleRun capture.

The SingleRun storage widget reports usage and capacity. It does not receive a
fresh host-attestation result, so it no longer displays a hard-coded claim that
quota enforcement is unverified. Production session admission still requires the
native host verifier's quota, firewall and reserve proof before container launch;
this change does not relax admission or the filesystem allowance.
